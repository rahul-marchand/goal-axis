# Goal-directedness 4YP

Research code for understanding **mechanistic goal-directedness**. Agents
trained on multi-objective mazes are behaviourally goal-directed: they trade
what an objective is worth against how far away it is. The project asks what
structure in the weights implements that, how well it can be understood, and
whether it can be used to make AI-safety-relevant decisions. The maze agents
(DRC, ResNet, ViT, and a behaviour-cloned prefix-LM, the "route model") and a
Craftax stage are the testbed; most of the code in this repo builds that
testbed. The project is less than halfway through, and the owner is currently
formalising the setup into a metric for LLMs (not in this repo yet).

Goal misgeneralisation was Experiment 1's subject ("do internals predict it
before behaviour?" was never tested directly). It is part of the record, not
the guide.

## Environment and tooling

Use `uv` for everything. There is no `pip install` step and no Docker.

```sh
uv sync                 # install (CPU)
uv sync --extra gpu     # install with CUDA JAX, on GPU machines
uv run pytest           # tests
uv run python ...       # anything else
```

Python is pinned to 3.11: far.ai's stack pins `jax==0.4.34`, `gymnasium~=0.29`
and `numpy~=1.26`, which do not all have wheels on newer interpreters.

## The training stack is a dependency, not a fork

`third_party/train-learned-planner` is a **git submodule pinned to a specific
commit**. Only the pointer is tracked in this repo.

**Never edit anything under `third_party/`.** Our code plugs in by subclassing
`cleanba.environments.EnvConfig` (environments) and `PolicySpec` (networks).
If something genuinely cannot be done without changing their code, raise it
rather than patching in place; it usually means we should subclass instead.

- `gym-sokoban` is **required** even though we never use Sokoban, because
  `cleanba/environments.py` imports it at module scope. It is installed from the
  nested submodule.
- `envpool` is **not** required and its nested submodule is deliberately left
  uninitialised. It is a heavy C++ build used only for fast Sokoban and is
  imported lazily inside `EnvpoolEnvConfig.make`.

## Known upstream limitations

### Evaluation assumes Sokoban

`cleanba.evaluate.get_cycles` asserts 3-channel square RGB observations, and its
caller assumes a positive reward means a box was pushed onto a target. Neither
holds here. Training runs fine and then dies at the first evaluation, and since
the exception is raised on the evaluation thread the process **hangs rather
than exiting**: it reads as a stall while still billing for the GPU.
`goalmisgen/configs/compat.py` adapts from our side; it is applied on importing
`goalmisgen.configs`.

**The evaluation path is not exercised by training tests.**
`test_training_survives_an_evaluation_pass` exists to run one; profiling runs
that set `eval_at_steps = frozenset()` do not cover it.

### The DRC head is not size-agnostic

`cleanba/convlstm.py` flattens the spatial dimensions before the MLP, and the
actor/critic heads are `nn.Dense` on that vector, so input dimensions are baked
into parameter shapes. Mazes are padded to a fixed maximum size. Size
generalisation would need a pooled or fully-convolutional head, added as a
`PolicySpec` subclass in our code.

### Gymnasium warnings, and `quiet.py`

cleanba reaches through a vector-env wrapper for `num_envs`,
`single_action_space` and friends, and gymnasium answers each access with a
deprecation warning. The sweeps redirect stderr into their results file, so
those warnings once made up most of `results/` by size, interleaved with the
rows (stripped on 2026-10-09, e2eeffd). Beyond bulk, they can push a header out
of reach of `provenance.parse_header` and break line-anchored parsers.

`goalmisgen/quiet.py` filters them on importing `goalmisgen`, the one place that
catches every entry point. It matches the deprecation phrasing rather than
raising gymnasium's log level, so a warning about *our* use of an environment
still gets through. pytest resets warning filters per test, so
`tests/test_quiet.py` asserts the filter directly.

## Level datasets

Generating a level costs ~3.5 ms (maze construction plus a BFS per objective);
stepping one costs ~10 µs. Real runs therefore use a pre-generated dataset:

```sh
uv run python scripts/generate_levels.py --n-levels 1000000 --out data/levels
```

Roughly 20-40 minutes on eight cores, a couple on 48, ~36 MB. Set
`MazeConfig.level_dataset` to the directory and reset becomes an array lookup.

- **One dataset serves an entire correlation sweep.** Layout, placement, values
  and distances do not depend on `feature_value_correlation`; only colour
  (`feature_id`) assignment does, and that happens at load time. Do not
  generate one dataset per ρ.
- **Datasets are fingerprinted** over the sampler config and the source of
  every module in `dataset.CONTENT_MODULES`. Editing any of them invalidates
  every dataset on the volume, and loading one raises `FingerprintMismatch`.
  Regenerate rather than disabling the check. Comments and docstrings are
  stripped before hashing, so prose edits are free. The hash is computed **once
  per process**, so a `git pull` mid-run cannot kill a long run (one 150M-step
  run died at 140M before this).
- **New feature schemes go outside `CONTENT_MODULES`** when they cannot change
  what a dataset contains. `ColourKeyedFeatures` lives in
  `envs/colour_keyed.py`, not `envs/features.py`, for exactly this reason.
- **Training and evaluation never share mazes.** Splits are by maze layout
  (`envs/splits.py`); `maze_drc33` trains on `train` and evaluates on `valid`.
  `split_by_layout` thresholds are fractions of the pool, so splits are only
  global at a fixed pool size: comparing across pools of different sizes needs a
  set held out from both (the overfit study hit this).

Datasets are directories of plain `.npy` files, not compressed archives, so
they can be memory-mapped and shared across actor processes; `LevelDataset`
pickles by path for the same reason. Do not "simplify" either.

**Generation pools are spawned, not forked.** The generators import
`configs.env`, which reaches cleanba and JAX, so the parent holds a
multithreaded JAX runtime by the time it builds a pool. Forking that deadlocks,
and it *hangs* rather than failing. Use `goalmisgen.parallel.worker_pool`,
never `mp.Pool` directly. The payload modules (`envs.dataset`, `offline.demos`,
the Craftax world and task) are deliberately JAX-free, which keeps the spawn
cheap; keep them that way.

## The agents: γ=1 bases and their arms

**Every current RL base is trained at γ=1** (the "g1" family; `001 --gamma`),
so it optimises the same undiscounted objective the solver and every metric
score: a threshold of `(v0 - v1) / 0.05` = 10 steps at values (1.0, 0.5). The
preset default is still γ=0.995. Arms inherit the base's discount from its saved
config (`configs/saved.py`); fine-tuning a g1 base at 0.995 would change the
quantity being measured. `analysis.behaviour.optimal_threshold(v0, v1,
step_penalty, gamma)` is the one definition of the task optimum.

Banked bases (details and the runs that were dropped are in `RUNS.toml`):

| family | bases |
|---|---|
| DRC | `novalue11g1.s1234`, `s9012`, `s3456e` (an extension of `s3456`) |
| ResNet | `resnet11nvg1.s1234`, `s2468`, `s3456` (`BASE.json` picks a healthy checkpoint; converged ResNets collapse late) |
| ViT | `vit11nvg1.s9012` only: n=1, the one of six that learned the trade-off |
| route model | `bcnv11.s1`-`s3` (offline; scaling twins `sc11.<d><L>`) |

The γ=0.995 runs (`novalue11.*`, `maze11.*`, `resnet11novalue.*`,
`vit11novalue.*`) remain as the record of Experiments 1-2. Judge a base by its
decoded threshold and reach, not by training success: `episode_successes`
rewards reaching *a* goal, and ViT duds looked converged while running to the
nearest one.

**Arm names** (`goalmisgen/volume.py`): `<sweep><offset>@<steps>[.r<k>]` under
the base, e.g. `o1+020@400k`. The budget is in the name because every
fine-tuning quantity scales with it. Sweep families:

- `o`: the symmetric grid the axis is fitted from;
- `x`: one-sided arms past preference parity;
- `k`: `x` with colour *i* pinned to objective *i* (colour keying);
- `m`: arms that move several values at once.

`x`, `k` and `m` are held out of every fit. Colour keying is a **property of
the `k` family**, not a flag: `CorrelatedFeatures` paints colour 0 on whichever
objective is worth more, so an unkeyed arm past parity learns a relabelled task
and its threshold turns at zero by construction. `.r<k>` is a fine-tune-seed
replicate (seed offset `1000*(k-1)`); the original carries no suffix.
`volume.iter_arms` is the one enumerator, and it hides replicates unless asked;
do not walk `arms/` by hand.

## Reading agents from scripts: the shared plumbing

Scripts and experiments are thin orchestration over the package. They import
from `goalmisgen`, never from another script or a numbered experiment, and they
do not rebuild an agent's environment from literals.

- **Where data lives**: `goalmisgen/paths.py`. `data_root()` is
  `$GOALMISGEN_DATA`, default `/workspace/data`; `run_dir`, `level_dataset`,
  `offline_demos` and friends build the canonical paths beneath it.
- **What an agent was trained with**: `configs/saved.py` reads the run's own
  `cfg.json` (value channel, discount, network, the whole `train_env`).
- **RL agents**: `goalmisgen/axis.py`, the twin of `offline/axis.py`.
  `load_base` reads `BASE.json`; `eval_config` is the run's own `train_env`
  with only the evaluation knobs replaced (levels, split, envs, seed), so a
  colour-keyed or legend agent is evaluated on what it was trained on;
  `load_sweep` gives the fitted family's arm diffs; `Greedy` rolls out and
  `read_threshold` turns outcomes into a threshold with its bootstrap interval.
  Where old scripts differed (float32 vs float64 write arithmetic, num_envs,
  bootstrap seeds), the difference is a parameter whose default at each call
  site reproduces that script's recorded results.
- **Route models**: `offline/axis.py` (`load_base`, `load_sweep`, `measure`).
- **Fine-tuning an arm**: `goalmisgen/finetune.py` (what `013` runs).
- **014-format tables**: `analysis/tables.py` is the one parser; figure
  parsers and reports use it rather than their own regexes.
- **Edit search backends** (RL and route model): `edits/backends.py`.
- **The legend observation** is `MazeConfig.observation = "legend"`, recorded
  in `cfg.json`; runs from before the field carry an `OBSERVATION` marker that
  `configs/saved.py` reads.

## Other architectures, the route model, the ladder

### `goalmisgen/nets`: other architectures, as `PolicySpec` subclasses

`TransformerSpec` is a ViT-style policy; `ScaledInputSpec` wraps any spec to
undo cleanba's input scaling. **The scaling is not cosmetic.**
`Policy._maybe_normalize_input_image` divides every observation by 255, because
cleanba's environments emit uint8 images. Ours are already in [0, 1]. The DRC
survives inputs of order 1/255 (its gates make the state O(1)); a ReLU ResNet
does not, and `resnet11` sat at entropy ln 4 for 25M steps before this was
found. Wrap a new spec in `ScaledInputSpec` unless it normalises its own input.
`Policy` reads `yang_init`, `norm`, `normalize_input` and `head_scale` from the
*outer* spec, so `presets.py` passes them to the wrapper explicitly; anything
else should too.

Probes read any architecture through `nets/readers.py`:
`state_reader_for(policy)` returns per-cell grids for the DRC's carry, a ResNet
stage or a transformer residual stream. Networks with no carried state have no
cell state, so anything that *writes* must check `has_cell_state` first.

### `goalmisgen/offline`: the route model

A prefix-LM trained on expert routes, sharing the levels, the solver and
`analysis.behaviour` with the RL agents. **The expert is undiscounted**
(`solve()` maximises `value - 0.05 x distance`), so the route model's optimum is
10 steps at the base values: the same as the g1 bases. Only comparisons with the
γ=0.995 agents (optimum ~9.3 steps) need to say which optimum they mean.

`done.json` is written after training returns and is what marks a run or arm
finished. `--init-from` carries **parameters only**; the optimiser starts fresh.
`offline/demonstrations.py` is the task boundary: the `Demonstrations` protocol
lists everything the trainer, decoder, axis fit and probes read, and
`load_demonstrations` picks the implementation from a `task.json` marker. A new
task implements the protocol; it does not fork the pipeline.

### The base-checkpoint ladder

`goalmisgen/base_ladder.py` (driven by `scripts/base_ladder.py`) re-runs a value
sweep from earlier checkpoints of one agent, to ask when the axis appears. A
rung is an ordinary agent, `runs/<agent>.at<steps>/BASE.json` plus a symlink to
the parent's checkpoints. Anything that resolves "the newest checkpoint"
instead of reading `BASE.json` will silently fit the parent's final agent.

**Ask for rungs by step count, not by name.** Checkpoint directories are padded
to `ceil(log10(total_timesteps))` digits, so 70,103,040 steps is `cp_070103040`
in a 150M run and `cp_70103040` in an 80M one. A hardcoded name that matched
nothing once made every run of a campaign skip a rung and report success.

(The arm-length ladder, `analysis/arm_length.py`, is a different ladder: over
fine-tune length, not base training.)

## Craftax is an engine, not a task

`craftax==1.6.1` is pinned exactly and used unmodified: we build its states and
step them. Everything of ours is in `goalmisgen/craftax/`; `docs/Craftax.md`
has the design and status.

- **Only `craftax/engine.py` imports Craftax or JAX.** World, task, planner and
  demonstration stores are numpy, so generation runs in the spawned
  `worker_pool`. `tests/test_craftax_engine.py` checks the import boundary in a
  subprocess.
- **The engine's vocabulary is mirrored by value in `blocks.py`** (block and
  action ids, move vectors, the solid set, the pickaxe rules) and
  `tests/test_craftax_blocks.py` asserts each against the real enums. Bump the
  pin, run that test.
- **Walls are bedrock** (`blocks.BEDROCK`, the furnace block: solid, unminable,
  inert in our recipes). Stone was mined through by a decoded model in 42% of
  its routes. Stone appears only as deposit tiles in the crafting task.
- **Stage 2 is a maze `Level` rendered into the engine** (walls bedrock, free
  cells grass, objectives ore). The ore is solid, so the expert route is the
  canonical maze route plus DO, with the final turn dropped after a straight
  approach: cost `d + 1` after a corner and `d` after a straight run. Each
  objective is costed by its own engine route, so the choice can differ from
  the maze's only on near-ties. `CraftaxDemoSet` is a `DemoSet` seen through a
  `CraftaxTask`, not a second store.
- **Experts are canonical** (`craftax/routes.py`): shortest paths with one
  fixed move preference, and a greedy crafting plan, so every expert decision is
  inferable from the map by a forward-emitting model.
- **Stage 4 is receding-horizon**: the model sees the current state (map,
  facing, inventory, and a channel for a placed table) and is decoded one action
  per pass with the engine in the loop (`craftax/closed_loop.py`).
- **The observation is a function of engine state** under hidden values; a test
  holds `engine.render` equal to the training observation.
- **The outcome dict is a superset of the maze's** (`walls_mined`,
  `wasted_actions`, `positions`). `analysis.behaviour` reads with `.get`, so a
  missing key would silently become NaN; the contract test catches it.
- **Ore-field datasets carry their own fingerprint** (`ore_field_fingerprint`).
  Nothing under `craftax/` is in `dataset.CONTENT_MODULES`, and nothing there
  may be edited to accommodate Craftax.
- **Engine facts the code leans on**, all tested: `OUT_OF_BOUNDS` is walkable
  (worlds are bordered with bedrock); the engine's own `reset` refuses maps
  under 16 cells (states are built by hand); DO facing grass rolls a sapling on
  the rng (replays use a fixed key); energy falls around step 31 and SLEEP then
  freezes the player (reported as wasted actions).

## Data, results and figures

**The repo holds code, write-ups, results tables and rendered figures.** Bulk
data lives on the RunPod network volume under `/workspace/data`: datasets,
runs, arms, and figure source data (npz and JSON) under
`/workspace/data/figures-data`. `/figures/data/` is gitignored for new files;
what was tracked before that policy stays tracked.

- `results/` holds the verbatim text (and some JSON) output of measurement
  runs. Each file written since `goalmisgen/provenance.py` names its producer in
  its header; `results/INDEX.md` is generated from those headers. Write why a
  table exists in `results/README.md`.
- **Figures pipeline** for the blog: `figures/src/<name>/build_fig.py` renders
  `figures/src/<name>/data.json` into `figures/fragments/<name>.html`, which is
  spliced into the post at `<!-- fig: name -->`. `data.json` comes from a parser
  or extractor that reads `results/` or the volume. **Builders deliberately do
  not share chart primitives**: the owner hand-tunes each one, so do not
  refactor them into a common module or edit one to serve another.

## RunPod

Every pod mounts the network volume `r96r190jsf` (EU-RO-1) at `/workspace`, and
runs `uv run` from `/workspace/GoalMisgeneralisation`. These rules each cost
money to learn:

- **Use the same image as every other pod**:
  `runpod/pytorch:1.0.3-cu1281-torch291-ubuntu2404`. All pods share one `.venv`
  on the volume, and uv silently rebuilds it (without the GPU extra) on a pod
  whose interpreter differs, breaking every running job. Check
  `runpodctl pod list` first.
- **Never `uv sync` from two pods at once.** Inside running jobs use
  `uv run --no-sync`. To repair a rebuilt venv, sync from one pod with
  `--extra gpu` and check `jax.devices()` shows a CUDA device.
- **Create pods with `--ports '22/tcp'`**, or they come up RUNNING and never
  accept ssh.
- **A create that times out may still have created a pod.** List before
  retrying.
- **Never leave a pod idle.** Delete it when its job finishes (from the Surface:
  the pod-side `runpodctl` is too old to delete), and **verify by listing**.
  Two pods once sat idle for three weeks.
- **`ulimit -n $(ulimit -Hn)`** at the top of any pod script on this image: the
  soft limit is 1024 and the async vector env dies with "Too many open files".
- **Two JAX jobs on one GPU need `XLA_PYTHON_CLIENT_PREALLOCATE=false`**; without
  it a cuSolver error most likely killed 24 of 32 jobs of one ladder.
- **`pkill -f pattern` or `pgrep -f pattern` inside an ssh command matches the
  ssh shell itself.** Bracket the pattern (`"[b]ase_chain"`) and verify a launch
  by the worker process or its log, not the wrapper.
- **Run long chains from a snapshot copy of the code**, not the shared checkout:
  another session edited the checkout mid-run once and invalidated a chain. Copy
  only `goalmisgen/ scripts/ experiments/ pyproject.toml` (not the 9 GB
  `.venv`), and push fixes to the snapshot the chain is running from.

## Design conventions

The environment is extended repeatedly (new correlation structures, objective
counts, distribution shifts, a second engine). The organising rule is that
**`MazeEnv` does not change**: it consumes a `Level` and steps it. Anything
experiment-specific goes behind a protocol in a swappable strategy object.

- `Level` fully specifies one episode; `LevelSampler` produces them. A new
  experiment is a new sampler, not an edit to an existing one.
- **Ground truth (BFS distances, optimal target) belongs in the `info` dict,
  never in the observation.** A test asserts this.
- Prefer small, typed, single-purpose modules. Favour clarity over cleverness
  and over premature optimisation; profile before optimising the env.
- Every layer gets tests before the next layer is built on it.

## Commit conventions

Commit to `main`. A session's work lands as a handful of themed commits (about
5-10 for a long session), each body listing its sub-changes and why -- not one
commit per edit, and not one mega-commit. Small working commits are fine if
they are squashed into themes before pushing. **Do not add `Co-Authored-By`
trailers or any other attribution to commit messages.**
